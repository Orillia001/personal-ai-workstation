# 执行与交付模式

用于内部改进、软件/产品、实施、部署、运营或其他已经准备进入执行的项目。目标是让团队知道交付什么、谁负责、何时完成、如何验证以及偏离时怎么办。

## 建议内容

1. 项目概览：发起原因、目标、赞助人/负责人、主要约束和成功定义。
2. 范围与非目标：项目起止边界、受影响流程/系统、明确不做事项。
3. 利益相关方与治理：决策权、执行责任、咨询/知会关系和升级机制；复杂项目可用 RACI。
4. 需求与验收：需求来源、优先级、可交付物、质量标准、验收人和证据。
5. 工作分解：按可交付成果组织工作包，避免只有零散活动清单。
6. 里程碑和依赖：阶段出口、关键依赖、外部输入、缓冲和关键决策点。
7. 资源与预算：人员能力、工时/数量、采购、环境、数据和资金约束。
8. 质量与验证：评审、测试、试点、验收、缺陷处理和完成定义。
9. 风险、问题与假设：负责人、触发条件、应对、应急方案和复查时间。
10. 沟通与变更：状态节奏、受众、报告内容、基线、变更批准和版本记录。
11. 上线/移交/运营：培训、迁移、回退、支持、维护责任和退役安排。
12. 成效评估：基线、目标值、数据来源、测量频率、收益负责人和复盘点。

## 粒度选择

- 低复杂度：一页项目章程 + 里程碑/责任/风险表。
- 中等复杂度：完整计划书 + 需求与证据追踪表。
- 高复杂度或高风险：在主计划之外维护详细进度、预算、风险、变更和验收基线，但主文档只保留决策所需摘要与链接。

没有可靠日期时使用相对工期和依赖条件，并标明排期假设。不要为了显得完整而捏造每日任务、资源利用率或精确成本。

项目计划的通用检查可参考 PMI 关于范围、工作分解、资源、里程碑、风险、验收和变更管理的概述：<https://www.pmi.org/learning/library/project-plan-assembly-elements-summary-3128>。以组织现行方法和项目合同为准。
