# Matt 工作流

本文件是工作站开发任务的路由与本地适配规则。桌面入口和实际工作站共用此文件。任务、技能步骤和验收以实际文件及结果为准。

## 开始任务

1. 运行 `./ws.ps1 context [项目] -Topic development`，确认 station_root、ready、warnings，读取返回的项目控制文件。继续执行 workstation-operator 的本地操作约束。
2. 从当前会话技能目录读取 `ask-matt/SKILL.md`，再读取所选技能的 SKILL.md。同一任务已读且未变的规则复用。开始时简短说明采用的流程。
3. 先确认本次验收结果和差异基准：有 Git 使用现有状态；无 Git 按下文建立修改前备份。现有未完成变更保留。

## 选择流程

| 当前任务 | 执行路径 | 完成依据 |
| --- | --- | --- |
| 明确的小功能或已有界面调整 | implement → code-review；有实际行为边界时调用 tdd | 可用产物、适用检查、双轴审查结果 |
| 需要先看到界面或验证交互 | prototype；选定方案后，明确进入实现时走 implement → code-review | 可运行原型、设计结论；正式实现另有验收 |
| 缺陷修复 | diagnosing-bugs → 修复与回归 → code-review；结束时 retro | 同一复现先失败后通过，保留回归依据 |
| 需求中存在影响方案的未决问题 | grill-with-docs，然后进入上述适用路径 | 问题已有结论，术语/决策按需记录 |
| 需要跨会话交付的明确需求 | to-spec → to-tickets → 按阻塞顺序 implement → code-review | 每票可验证、依赖已解决、整体验收 |
| 规模很大且方向尚不明确 | wayfinder，决策明确后转规格与任务 | 决策记录及明确的后续实现范围 |

按会话已有信息推进，需求已经明确时直接采用。只有缺失信息确实影响结果，或所选技能仍有适用的未满足确认要求时，提出必要问题。技能的安装、读取或名称出现不能替代实际执行。

日常教学、学习进度查询、文件整理、资料阅读和普通文档输出继续使用其原有入口；其中涉及代码、UI或架构实现的部分再进入本流程。

## 实现与验证

任务事实源见 [issue-tracker.md](issue-tracker.md)，术语及决策读取规则见 [domain.md](domain.md)。明确的小功能可直接以用户请求和验收条件作为规格依据，复杂任务按对应技能生成规格及任务单。

常规行为验收优先使用浏览器中的用户操作、现有 HTTP API 或 CLI 公共接口。新增边界时按 tdd 的适用要求确定。需要自动回归的逻辑先运行会失败的行为测试，再实现使其通过；只有修复后补测时如实记录。低影响的文字或样式调整采用相应预览/语法检查。

code-review 的 Standards 与 Spec 分别报告：前者核对项目规范与实现质量，后者核对用户需求及规格。执行时读取该技能；按技能要求和当前会话能力使用独立审查代理。默认单Agent执行其他工作；会话限制不允许独立审查时，分别完成两轴审查并标明独立性限制。

## 没有 Git 时

当前工作站没有 Git 仓库，使用可验证的文件差异作为本地适配：

- 修改前将本次涉及的现有文件复制到 `Backups/<运行ID>/`，记录原路径、备份路径和 SHA-256；新文件记录为新增。记录待审文件清单，避免把其他任务的变化混入。
- 实现后对该基准生成逐文件差异，结合任务的用户请求或规格执行 Standards / Spec 两轴审查。报告写明“基于备份差异的适配审查”，并保留差异和审查结果。
- 该适配没有执行 Git 原生的 HEAD/merge-base 审查步骤。已有 Git 仓库时按技能使用真实基准；提交、推送和发布继续遵守已有授权规则。

## 完成任务

记录实际采用的技能、产物、验证命令/结果、两轴审查及限制，更新目标项目的 `12-status.md` 并报告运行ID。复杂实现或发生流程遗漏时执行 retro，将可验证的改进落实到入口、检查或规范中。

本地任务约定及这些入口规则即为已完成的 Matt 初始化；新会话直接使用。只有需要切换任务平台或领域文档布局时才重做 setup。
